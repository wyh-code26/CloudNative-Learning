今日精读：Service — 为应用提供稳定的“网络名片”

原文 (Kubernetes 官方文档)

An abstract way to expose an application running on a set of Pods as a network service.
With Kubernetes you don't need to modify your application to use an unfamiliar service discovery mechanism. Kubernetes gives Pods their own IP addresses and a single DNS name for a set of Pods, and can load-balance across them.

中文翻译

Service 是一种将运行在一组 Pod 上的应用暴露为网络服务的抽象方法。有了 Kubernetes，你无需修改应用程序就能使用服务发现机制。它为 Pod 提供独立 IP，并为一组 Pod 提供统一的 DNS 名称，还能在它们之间做负载均衡。

核心词汇提取

术语 解释
Service (服务) 一组 Pod 的统一访问入口，提供固定的虚拟 IP 和 DNS 名称。
Pod IP (Pod 地址) 临时地址，Pod 重启或被替换后会改变。
DNS Name (域名) Service 在集群内被分配一个固定的域名，如 my-svc.default.svc.cluster.local。
Load-balance (负载均衡) 将流量均匀分发到后端健康的 Pod 上，通过 iptables 或 IPVS 规则实现。

底层原理与《密盾》项目映射

Service 的核心作用是解耦“服务身份”和“服务实例”，这和你用 Nginx 做的事情一模一样。

· 映射一：Service 的固定入口 ↔ 你的 Nginx 反向代理
  你的《密盾》后端容器 midun-zkp 监听在 127.0.0.1:8090。无论容器怎么重启，只要 Nginx 的 proxy_pass 指向它，前端就不用改代码。Service 在 K8s 内部就是那个“反向代理”，为后端 Pod 提供永不改变的虚拟 IP (ClusterIP) 和 DNS。
· 映射二：Service 的负载均衡 ↔ 你未来的多副本部署
  你现在只有一个后端容器。如果将来流量增大，需要跑 3 个容器，就得手动配置 Nginx 的 upstream。Service 把这个过程自动化了——你只需在 YAML 里声明 selector: app: midun，它就会自动发现和分发流量给健康的 Pod。

面试锚点

Q: 为什么需要 Service？直接用 Pod IP 不行吗？
A: Pod IP 是临时的，Pod 重启后 IP 会变。如果前端依赖 Pod IP，每次重启后都要更新配置。Service 提供了一个固定的虚拟 IP 和 DNS 名称，无论后端 Pod 怎么变，前端的访问入口始终不变。这是云原生架构中实现高可用和服务发现的核心设计。
