今日精读：Service — 集群内部的“网络抽象层”

原文 (Kubernetes 官方文档)

An abstract way to expose an application running on a set of Pods as a network service.
With Kubernetes you don't need to modify your application to use an unfamiliar service discovery mechanism. Kubernetes gives Pods their own IP addresses and a single DNS name for a set of Pods, and can load-balance across them.

中文翻译

一种将运行在一组 Pod 上的应用程序公开为网络服务的抽象方法。使用 Kubernetes，你无需修改应用程序即可使用服务发现机制。Kubernetes 为 Pod 提供它们自己的 IP 地址，并为一组 Pod 提供单一 DNS 名称，还能在它们之间进行负载均衡。

核心词汇提取

术语 解释
Service (服务) 一组 Pod 的统一访问入口，提供固定的虚拟 IP 和 DNS 名称。
Pod IP (Pod 地址) 每个 Pod 独有的 IP 地址，但 Pod 重启后地址会变化。
DNS Name (域名) Service 被分配一个固定的集群内部域名，如 my-svc.default.svc.cluster.local。
Load-balance (负载均衡) 将流量均匀分发到后端多个 Pod 上，通过 kube-proxy 维护的 iptables/IPVS 规则实现。

底层原理与《密盾》项目映射

Service 的本质是在前端和后端之间增加了一个稳定的网络抽象层，让前端的连接目标永远不变，即使后端的 Pod 因为升级、重启、扩缩容而不断变化。

· 映射一：Service 的固定虚拟 IP ↔ 你的 Nginx 反向代理
  你的《密盾》容器 midun-zkp 监听在 127.0.0.1:8090。无论容器怎么重启，只要 Nginx 的 proxy_pass 指向这个地址，谢海峰的前端就不用改任何代码。Service 在 K8s 集群内部扮演的正是这个“反向代理”的角色——它给后端 Pod 提供一个永远不变的虚拟 IP（ClusterIP），前端的请求先打到这个虚拟 IP 上，再由 kube-proxy 根据 iptables 规则转发到某个具体的 Pod IP。
· 映射二：Service 的负载均衡 ↔ 你未来的多副本部署
  你现在只有一个 midun-zkp 容器。如果未来流量增大，你需要同时跑三个容器，就得手动配 Nginx upstream 并维护三个容器的地址。Service 把这个过程自动化了——你只需在 YAML 里声明 selector: app: midun，Service 就会自动发现所有带这个标签的 Pod，并在它们之间分配流量。当某个 Pod 挂了，Service 自动从后端池中剔除它；当新 Pod 启动，Service 自动把它加入后端池。这就把你昨天手写的那份《服务器宕机恢复清单》里的手动步骤，全部升级成了自动化的自愈机制。
· 映射三：Service 的 DNS 名称 ↔ 你的 zkp.wuyuhangcn.com 域名
  你给《密盾》绑定了一个公网域名，任何人通过这个域名就能访问，不用记 IP。Service 在集群内部也做同样的事——它被分配一个固定的 DNS 名称（如 midun-api.default.svc.cluster.local），集群内的任何 Pod 都能通过这个名字调用它，彻底解耦了“服务身份”和“服务位置”。

面试锚点

Q: 为什么需要 Service？直接用 Pod IP 不行吗？
A: Pod IP 是临时的，Pod 重启、升级、迁移时 IP 会变。如果前端直接依赖 Pod IP，每次 Pod 重建后都要更新配置。Service 提供了一个固定的虚拟 IP 和 DNS 名称，无论后端 Pod 怎么变，前端的访问入口始终不变。这是云原生架构中“解耦服务身份与服务实例”的核心设计模式。
